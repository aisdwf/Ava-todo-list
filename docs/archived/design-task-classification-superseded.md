## 1. 设计原则（本文的裁决标准）

按优先级排列。当下述原则冲突时，序号小者优先：

1. **零必填铁律**。任何时刻，用户都能只输入一句话就完成任务创建。
   项目、标签、deadline **全部可空**，且留空的任务是完全正常的一等公民，
   不得在 UI 上被标记为「不完整」「待补充」或以任何方式催促补全。
2. **小窗优先**。小窗是唯一差异化立足点（REQUIREMENTS §3.1）。
   当小窗与主窗口的设计取舍冲突时，优先保障小窗。
3. **渐进披露**。高级能力（项目管理、标签编辑）不得出现在主路径上，
   仅在用户主动进入时展开。简洁性由「默认不可见」保障，而非由「功能少」保障。
4. **通用预期优先于新颖**。用过同类工具的人应能零学习上手（REQUIREMENTS §3.2）。

## 2. 数据契约

### 2.1 前置技术验证：加字段无需手写迁移

**已实测确认**（临时项目验证后清理）：`sqlite-net-pcl` 1.9.172 的
`CreateTable` 对已存在的表新增列时，自动执行 `ALTER TABLE ADD COLUMN`，
返回 `CreateTableResult.Migrated`，**既有行数据完整保留，新列取默认值**。

实测输出：

```
V1 建表并写入 1 行。行数 = 1
V2 CreateTable 返回：Migrated
V2 读取行数 = 1
  Id=abc Title=既有任务 Priority=2 ProjectId=NULL SortOrder=0
物理列：Id, Title, Priority, ProjectId, SortOrder
```

**结论**：本设计新增字段**不需要迁移脚本**，现有 `flowtask.db` 数据自动兼容。

**同时确认的能力边界**：`sqlite-net-pcl` **无关系映射能力**
（无 `OneToMany` / `ManyToMany` / `GetChildren`，全库仅一个 `CollationAttribute`）。
因此所有关联必须**手写查询与组装**，不存在导航属性。
这直接影响 §2.3 标签方案的选择。

### 2.2 项目：独立实体

**决策**：新增 `Project` 实体，独立表存储。

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `Id` | `string` | 主键，GUID |
| `Name` | `string` | 项目名，用户可重命名 |
| `ColorHex` | `string` | 项目色，用于列表左侧色条与筛选标识 |
| `SortOrder` | `int` | 侧边栏中的排列顺序 |
| `IsArchived` | `bool` | 归档而非删除，避免关联任务失去归属 |
| `CreatedAt` | `DateTime` | 创建时刻（UTC） |

**任务侧**：`TaskItem.ProjectId` 为**可空外键**（`string?`）。
`null` 表示「未归属任何项目」—— 这是默认状态，对应原则 1。

**为什么项目值得作为独立实体**（用户判断，此处补充设计依据）：
项目需要重命名（改一次，所有关联任务同步生效）、需要颜色标识、
需要在侧边栏列举与排序、需要归档。这些都要求它有独立身份。
若退化为字符串标记，重命名将退化为「批量查找替换」，且无法承载颜色与排序。

**删除与归档的分工（已确认）**：用户确认**需要删除能力**。二者并存，语义不同：

| 操作 | 语义 | 对其下任务的影响 |
| :--- | :--- | :--- |
| **归档** | 项目已完成，不再活跃，但历史归属有保留价值 | 任务保留，`ProjectId` 不变，仍可显示项目归属 |
| **删除** | 项目建错了或不再需要，其归属信息无价值 | **任务保留**，`ProjectId` 置 `null`，退回「未归属」状态 |

**关键约束：删除项目绝不删除其下任务。**
任务是用户的核心资产，项目只是它的一个可选属性。
删除一个属性不应销毁拥有该属性的实体。

**实施要求**：删除项目时须以单个事务完成
「置空关联任务的 `ProjectId`」与「删除项目行」两步，
避免中途失败留下悬空外键。
若项目下有任务，删除前须明确告知将影响多少条任务并要求确认 ——
这是不可逆操作（`Project` 无软删除标记）。

**为什么不给项目也加软删除**：那会引出「项目回收站」，
而项目本身是低频操作的轻量实体，为其建立完整的删除-恢复生命周期
属于过度设计（原则 3）。任务不被销毁已经消除了删除操作的主要风险。

**一个任务只能属于一个项目**。这是「项目」一词的通用预期（原则 4），
也与「多维分类交给标签」的分工一致（§2.3）。

### 2.3 标签：轻量附加

**决策**：标签**不设独立实体表**，以分隔符拼接的字符串存于 `TaskItem.Tags`。

**为什么不建标签表 + 关联表**：
标准做法是 `Tag` 表 + `TaskTag` 多对多关联表。但 §2.1 已确认
`sqlite-net-pcl` 无关系映射能力，多对多需手写关联表的增删改查与 JOIN 组装，
且每次读取任务列表都要额外查询与内存拼装。
对一个本地单机、任务量级在千条以内的应用，这个复杂度换不来相应收益（原则 3 的成本侧）。

标签的定位是**轻量**（用户原话「其他可以作为附在 todolist 的标签」），
它不需要重命名、颜色、排序 —— 那些是项目的职责。
职责分工清晰，实现方案就应随之简化。

**存储格式**：
- `TaskItem.Tags` 为 `string?`，`null` 或空串表示无标签；
- 多个标签以 `,` 分隔，各标签内部禁止出现 `,`（输入时过滤）；
- 大小写不敏感去重，但保留用户首次输入的原始大小写用于显示。

**已知代价，明确接受**：
- 无法重命名标签（改名需逐条任务修改）；
- 存在拼写不一致产生近似重复标签的可能（`bug` vs `Bug` 由大小写不敏感去重缓解，
  但 `紧急` vs `急` 无法避免）；
- 按标签筛选需 `LIKE` 匹配，无法利用索引。任务量级下可接受。

**缓解措施**：输入标签时提供已有标签的自动补全建议
（从现存任务中提取全部标签去重），降低拼写发散概率。

**若未来标签量级或治理需求上升**，再升级为独立实体表，
届时是一次有明确证据支撑的独立演进 —— 而非现在为假想需求预付复杂度。

### 2.4 Deadline

**决策**：沿用现有 `TaskItem.DueDate`（`DateTime?`），补齐 UI 写入路径。

语义与时区处理**沿用 design-domain-contract §5 的结论**（该结论基于代码事实，未被需求推翻）：

- `DueDate` 表达「用户日历上的哪一天」，是**日期**而非时刻，存本地日期语义；
- `CreatedAt` / `CompletedAt` 表达「事件发生的时刻」，存 UTC；
- 两类字段基准不同是有意设计，源于语义本质差异，强行统一才是错误。

**须同时整改的既有缺陷**（详见
[design-domain-contract（技术缺陷已并入）](./design-task-domain-superseded.md)）：
`GetTodayTasksAsync` 用 `DateTime.Today.ToUniversalTime()` + 24h 计算「今日」，
在非 UTC 时区下区间错位，且直接依赖系统时钟违反
[AI_CONSTITUTION](../../AI_CONSTITUTION.md) Article 9，需引入可注入 `IClock`。

### 2.5 契约变更汇总

`TaskItem` **新增两列**（`ProjectId`、`Tags`），无删除、无类型变更：

```
TaskItem: Id, Title, Description, IsCompleted, Priority, DueDate,
          CreatedAt, CompletedAt, IsDeleted,
          + ProjectId (string?)      ← 新增
          + Tags (string?)           ← 新增
```

**新增 `Project` 表**。

依 §2.1 实测，二者均由 `CreateTable` 自动处理，**无迁移脚本，历史数据自动兼容**。

`Description` 字段（现为死字段）在本设计中**继续保留但不启用** ——
它属于「任务详情」范畴，与本文的分类主题正交，
避免把无关改动混入本次变更边界（Article 10）。
它仍是显式登记的待办，不因本文而消失。

## 3. 简洁性如何保障

用户要求「需要考虑到 todolist 本身的简洁性，必须支持什么都不做直接随手记」。
这是对新增分类能力的**约束条件**，需具体设计手段落实，不能仅停留在口号。

### 3.1 三条硬性约束

1. **主输入路径不新增任何控件**。主窗口的快速添加栏与小窗输入框
   保持当前形态（输入框 + 优先级三选），**不添加项目下拉、不添加标签输入、
   不添加日期选择器**。
2. **无必填校验**。除标题非空外，不存在任何校验阻止任务保存。
3. **无补全催促**。UI 不得对缺失项目/标签/deadline 的任务做视觉标记或提示。

### 3.2 分类信息的录入时机

分类不在**创建时**录入，而在**创建后按需补充**：

- 主窗口：点击任务行展开编辑态，其中包含项目、标签、deadline、备注；
- 这符合真实使用节奏 —— 灵感来时先记下，整理时再归类。

**代价**：明确知道归属的任务无法一步创建到位（先建后归类，两步）。
**接受理由**：原则 1 优先级最高。为少数「创建时已知归属」的场景
在主路径上添加控件，会损害全部创建操作的速度。

**缓解方向：输入语法（已认可，初版不做）**

形如 `修 bug #FlowTask @紧急` 的内联语法，可在不新增任何控件的前提下
让一步到位成为可能 —— 这是它与「加下拉框」的本质区别：
**它不占用界面空间，因而不违反 §3.1 的硬性约束。**

**用户明示**：「初步可以不做，但是我觉得这是一个正确的方向。后续可以纳入考虑。」

**初版不实现的理由**：需要解析器、实时高亮反馈、
以及「项目不存在时是否自动创建」等一系列决策，实现量不小。
且它是隐式知识，须配合可发现的提示才不违反原则 4（零学习上手）。

**初版须为此预留的结构**（不实现功能，但不得挡路）：

1. 任务创建逻辑须集中在单一入口，而非在主窗口与小窗各写一份 ——
   否则未来语法解析要接两处（Article 6）；
2. 标题文本在保存前**不做任何字符过滤或转义**，
   保持原样落库，避免未来 `#` / `@` 被提前处理掉。

> **注意与 §2.3 标签分隔符的潜在冲突**：标签以 `,` 分隔存储。
> 若未来语法采用 `@标签` 形式，须确认用户输入的标签文本本身不含 `,`
> （§2.3 已规定输入时过滤）。此约束在初版即须落实，
> 否则未来引入语法时会遇到已污染的历史数据。

### 3.3 「零分类」状态必须是完整体验

若用户从不使用项目与标签，应用体验应与当前完全一致：

- 侧边栏项目区在无任何项目时**整块隐藏**，不显示空列表或「新建项目」占位；
- 任务行在无项目、无标签、无 deadline 时不显示任何相关元素，
  与当前的行布局视觉一致；
- 筛选视图保持「全部 / 今日 / 已完成」三项不变。

## 4. 随手记小窗改造

### 4.1 现状与改造性质

当前小窗为 **620×150 的纯输入胶囊**，无列表区域
（`src/FlowTask.Desktop/Views/QuickCaptureWindow.axaml`）。
需求 R-1.1 / R-1.2 要求它能查看并勾选任务，属**结构性改造**。

### 4.2 阻塞性技术障碍：整窗拖拽与列表点击冲突

**这是本次改造必须首先解决的问题。**

现状：`QuickCaptureWindow.axaml.cs:31` 对整个窗口注册了 `PointerPressed`，
任意左键按下即调用 `BeginMoveDrag`：

```csharp
PointerPressed += (_, e) =>
{
    if (e.GetCurrentPoint(this).Properties.IsLeftButtonPressed)
    {
        BeginMoveDrag(e);
    }
};
```

**若直接加入任务列表，点击勾选框会被解释为拖动窗口，勾选功能完全不可用。**
这类缺陷不会被编译或现有测试捕获（spec-editorial-and-ripple-theme 的经验教训 1：Avalonia 静默失败），
必须在设计阶段显式处理。

**决策**：设立**专用拖拽区**替代整窗拖拽 ——
窗口顶部保留一条明确的拖拽握柄区域，仅该区域触发 `BeginMoveDrag`；
列表区与输入区不响应拖拽。

**实施注意**：Avalonia 的 `PointerPressed` 沿可视树冒泡，
在子控件处理后仍会到达窗口级处理器。因此除限定拖拽区外，
列表项的指针事件需正确标记 `Handled`，二者缺一不可。
此处须在实现时以实机点击验证，不可仅凭编译通过判定。

### 4.3 布局：输入区 + 列表区

**决策**：小窗纵向分为固定输入区（顶部）与可滚动列表区（下方）。

- **输入区**：保持现状（`✦` 图标 + 贯穿式输入框 + P1/P2/P3 + 快捷键提示）；
- **列表区**：展示任务，每行为「勾选圈 + 标题」的极简形态。

**窗口尺寸**：宽度维持 620，高度由列表内容动态适应，设上限（超出则滚动）。
**须决策**：上限取值。过高会让小窗失去「浮窗」特质、遮挡工作区域。
本文倾向**限制在 5～7 行**可见，超出滚动。

### 4.4 小窗显示哪些字段（关键决策）

这是决定小窗行布局、也是本次「少一次返工」的核心点。

**决策**：小窗任务行**仅显示勾选圈、标题、以及项目色条**。

**不显示**：标签、deadline 文本、优先级标签、创建日期。

**理由**：

- 小窗的职责是「快速打勾和查看」，不是「审阅任务全貌」。
  堆叠字段会使其退化为主窗口的缩小版，丧失存在意义（原则 2）；
- **项目色条**是唯一例外：它以 2～3px 的色条承载归属信息，
  零文本、零额外行高，是信息密度最高的表达方式；
- deadline 与优先级影响的是**排序**（哪些任务出现在小窗顶部），
  而非**显示** —— 其价值通过排序已经传递，无需占用横向空间。

**这一决策使小窗行布局对未来的字段扩展保持稳定**：
新增字段默认不进入小窗，除非有明确理由推翻本条。

> **与 §4.5.1 项目切换的关系（须留意）**：
> 若未来实现「单项目展示 + 多项目切换」，小窗在任一时刻只展示单个项目的任务，
> 此时**行内项目色条会退化为无信息量**（同一视图内所有行颜色相同）。
> 届时项目归属应上移至窗口级标识（如标题区显示当前项目名与色点），
> 行内色条相应移除。
>
> 这不影响初版实现 —— 初版展示全部未完成任务，色条承载真实信息。
> 但实现时应将「项目归属的视觉表达」收敛在单一处，
> 避免日后同时存在窗口级与行级两套表达（Article 6）。

### 4.5 小窗展示哪些任务

**决策（已确认）**：展示**全部未完成任务**，按 deadline 与优先级排序，取前 N 条。
**不限定**为「今日 + 逾期」。

理由：小窗定位是日常快速处理。若按今日过滤，
无 deadline 的任务（依原则 1 这是默认状态）将永不出现在小窗，
使小窗对大多数任务失效 —— 这会重演「今日聚焦恒为空」的同类错误。

**勾选后的行为**：任务立即标记完成并**从列表移除**，
须有短暂的视觉过渡以确认操作，不可瞬间消失（否则用户无法确认点对了哪条）。

### 4.5.1 后续方向：单项目展示与多项目切换

**用户明示**：「如果想做的好一点可以做单项目展示和多项目切换的能力，初版可以先不考虑。」

**初版不实现**，但记录为已认可的演进方向，避免初版做出阻碍该方向的结构决策。

设想形态：小窗在任一时刻只展示单个项目的任务，
通过快捷键（如 `Tab` 或 `←` / `→`）在项目间循环切换，
窗口级标识当前项目。这会让小窗从「全局待办速览」
变为「聚焦单一上下文的工作面板」，与「同时推进多个项目」
的用户特征（REQUIREMENTS §2）契合。

**初版须为此预留的结构**（不实现功能，但不得挡路）：

1. 小窗的任务查询须可按 `ProjectId` 过滤 —— 即查询层参数化，
   而非硬编码「取全部未完成」；
2. 项目归属的视觉表达收敛在单处（见 §4.4 注），
   便于日后从行级色条切换为窗口级标识；
3. 键盘导航的按键分配须为项目切换留出可用组合 ——
   `Tab` 若在初版被占用于「焦点回输入框」，
   需评估与未来项目切换的冲突（见 §4.6）。

**不预留的部分**：不为此提前引入配置项、不提前建抽象层。
预留仅限于「不做出需要推翻的决定」，而非「提前搭好骨架」。

### 4.6 键盘全程可达（R-1.4）

| 操作 | 按键 | 现状 |
| :--- | :--- | :--- |
| 保存并关闭 | `Enter` | 已有 |
| 关闭 | `Esc` | 已有 |
| 连续添加（保存不关窗） | `Shift+Enter` | 缺失，design-visual-language 已承诺 |
| 焦点移入列表 / 上下移动 | `↓` / `↑` | 缺失 |
| 勾选当前选中项 | `Space` | 缺失 |
| 焦点回到输入框 | `↑` 至顶 | 缺失 |

**须注意**：`↓` 需与输入框的文本光标移动区分。
输入框为单行，`↓` 无文本导航语义，可安全用于移出焦点至列表。

**`Tab` 键的处置**：本文**不将 `Tab` 分配给「焦点回输入框」**，
改由 `↑` 至列表顶部时自动回到输入框。
理由：`Tab` 是未来项目切换（§4.5.1）最自然的候选按键，
提前占用会导致该功能落地时被迫改变已被用户习得的键位。
`Tab` 在初版保留为 Avalonia 默认的焦点遍历行为，不做自定义。

### 4.7 呼出方式的缺口

R-1.4 要求全程无鼠标，但**呼出小窗当前依赖点击主窗口的按钮**
（`MainViewModel.OpenQuickCapture` → 视图层弹窗），
主窗口不在前台时无法唤起。

真正的解决需要**全局系统级快捷键**，而它已被 REQUIREMENTS §6 列为
需独立 ADR 的事项（涉及各平台原生 API 与权限模型）。

**本设计的处置**：小窗内部键盘闭环（§4.6）属本设计范围，
**全局呼出不在本设计内**，须独立立项。
在此之前 R-1.4 只能部分满足 —— 这是显式记录的缺口，不是遗漏。

## 5. 主窗口分类交互

### 5.1 侧边栏结构

现有侧边栏为「VIEWS：全部 / 今日 / 已完成」。**新增项目区**：

```
VIEWS
  全部任务          [12]
  今日聚焦
  已完成归档        [34]

PROJECTS                    ← 无项目时整块隐藏（§3.3）
  ● FlowTask        [5]
  ● 学习            [3]
  + 新建项目
```

**筛选维度关系**：项目筛选与 VIEWS 筛选**正交**。
选中项目时，展示该项目下的未完成任务。

> **须警惕的既有教训**：`TaskFilter` 枚举曾把「设置页」混入任务筛选维度，
> 导致视图模式与数据筛选耦合，已在 spec-editorial-and-ripple-theme 中修正
> （见 `MainViewModel.cs:16-21` 的注释）。
> 本次新增项目筛选**不得**塞入 `TaskFilter` 枚举，
> 须另立正交状态表达「当前选中的项目」。

### 5.2 任务行的分类呈现

任务行在保持 Editorial 排版留白的前提下增量显示：

- **项目**：行左侧 2～3px 竖向色条。无项目则无色条；
- **标签**：标题右侧小号弱化文本。无标签则不占位；
- **deadline**：标题下方或右侧，逾期以强调色区分。无 deadline 则不显示。

**约束**：以上元素**全部缺失时，行布局必须与当前完全一致**（§3.3）。

**须遵守的视觉契约**：新增元素必须复用 spec-editorial-and-ripple-theme 建立的令牌体系
（`Tokens.Shared/Light/Dark.axaml`），严禁新造并行令牌词汇 ——
该问题曾导致 spec-editorial-and-ripple-theme 首轮实现视觉全面失效（其 §1.1 根因分析）。

### 5.3 编辑态（R-2.4）

任务创建后可编辑，是当前的基础功能空洞。
沿用 design-domain-contract §4.2 的**行内展开式编辑**方案（该方案未被需求推翻）：
点击任务行主体展开，含标题、项目、标签、deadline、优先级；
勾选圈与删除按钮保留独立热区，避免与展开手势竞争。

保存语义沿用 design-domain-contract §4.3：**即时保存，无「取消」，不实现撤销**
（本地 SQLite 写入微秒级，显式保存按钮反而引入「未保存状态」这一额外状态机）。

空标题处理沿用 design-domain-contract §4.4：清空并失焦时**恢复原标题**，
与创建路径的空白静默忽略保持一致（Article 6）。

### 5.4 项目管理入口

依原则 3（渐进披露），项目的增删改**不占用主界面空间**：

- 新建：侧边栏「+ 新建项目」；
- 重命名 / 改色 / 归档 / 删除：项目右键菜单或其详情视图。

**须决策**：项目管理是独立视图还是轻量弹层。
本文倾向**轻量弹层** —— 项目属性仅名称与颜色两项，独立视图过重。

## 6. 非目标（本设计明确不做）

| 不做 | 理由 |
| :--- | :--- |
| 项目层级（子项目） | 扁平项目尚未验证够不够用，层级会波及全部查询与筛选逻辑 |
| 一个任务属多个项目 | 与「项目」的通用预期冲突（原则 4），多维分类由标签承担 |
| 标签重命名 / 标签颜色 / 标签管理页 | 标签定位为轻量（§2.3）。需要这些能力说明它应该是项目 |
| 输入语法（`#项目` `@标签`） | **初版不做，但用户已认可为正确方向**，后续纳入考虑。初版预留结构见 §3.2 |
| 小窗单项目展示 + 多项目切换 | **初版不做，用户已认可为演进方向**。初版预留结构见 §4.5.1 |
| 全局系统级快捷键 | REQUIREMENTS §6 已列为需独立 ADR 事项（§4.7） |
| 启用 `Description` | 与分类主题正交，避免混入变更边界（§2.5） |
| 撤销 / 重做 | 沿用 REQUIREMENTS §6 排除 |
| 手动拖拽排序任务 | 排序由 deadline + 优先级确定性决定，手动排序需持久化序号，独立立项 |

## 8. 实施风险

1. **小窗拖拽冲突（§4.2）** —— 最高风险。若未妥善处理，勾选功能完全不可用，
   且不会被编译或单元测试捕获，必须实机点击验证。
2. **Avalonia 静默失败** —— spec-editorial-and-ripple-theme 的经验教训 1：未定义的 `DynamicResource`
   与未匹配的样式选择器既不报错也不警告。本次新增大量 UI 元素（项目色条、
   标签、编辑态、项目弹层），凡引入新样式类或资源键须同步确认定义存在。
3. **交互路径的测试覆盖** —— spec-editorial-and-ripple-theme 的经验教训 4：脚本化点击在 macOS 上
   受辅助访问权限限制，「启动不崩」不能冒充功能验证。
   小窗勾选、编辑态展开、项目切换均为必须点击才触发的路径，
   须以 headless 测试覆盖代码路径，或如实声明未验证交由人工。
4. **筛选状态耦合** —— 项目筛选须独立于 `TaskFilter` 枚举（§5.1），
   否则重演 spec-editorial-and-ripple-theme 修正过的耦合缺陷。

## 9. 建议的实施拆分

批准后建议拆为三个可独立验证的 SPEC，按序推进：

| 顺序 | SPEC 主题 | 理由 |
| :--- | :--- | :--- |
| 1 | 数据契约扩展 + `IClock` 整改 + 编辑态 | 契约先落地，后续两项才有稳定基础。含 R-2.2 / R-2.4 与既有时区缺陷整改 |
| 2 | 主窗口分类交互（项目区、任务行呈现、项目管理） | R-2.1 / R-2.3 / R-2.5 |
| 3 | 小窗改造（拖拽区、列表、勾选、键盘导航） | R-1.1～R-1.3。放最后是因为它消费前两项的成果，此时字段已稳定，一次做对 |

> **关于打包（R-3）**：建议置于全部功能完成之后。
> 它完全独立、随时可做，但每次功能变更后都需重新出包验证，
> 提前进行等于重复劳动。
> 现有 `publish/win-x64/` 产物为 framework-dependent，未达 R-3.2，需整改。
