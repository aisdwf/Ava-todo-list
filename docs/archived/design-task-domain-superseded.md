### 1.3 为什么范围大于「到期日交互」

## 2. 设计原则

本次功能设计遵循的取舍标准，用于裁决后续所有细节争议：

1. **捕捉零摩擦优先于结构完备**。随手记路径上不得新增任何必填项。
   任何新字段都必须可留空，且留空时任务仍然是一等公民。
2. **一个概念只有一处真源**。字段语义、默认值、显示格式均单点定义（Article 6）。
3. **不引入无法完成生命周期的概念**。若某字段没有创建、查看、修改、清除的完整路径，
   则本轮不引入（Article 10）。
4. **业务分支不依赖不可注入的外部状态**。时间判断必须经抽象注入（Article 9）。
5. **数据可恢复优于数据整洁**。删除路径必须保留用户挽回的机会。

## 3. 决策一：任务字段边界

### 3.1 时间字段：只保留单一 `DueDate`，不区分「计划日 / 到期日」

**决策**：保留现有 `DueDate` 单字段，语义明确为「**用户期望在这一天处理它**」。
不引入 `ScheduledDate` / `StartDate` 等第二时间维度。

**为什么**：
双时间维度（Things 3 的 "When" vs "Deadline"）解决的是长周期项目管理问题 ——
「这个任务我周三开始做，但周五才截止」。这对一款以「灵感速记」为核心定位的工具是过度设计：
它会让每个任务的时间录入从一次决策变成两次决策，直接违背原则 1。

若未来确实需要区分，那是一次有明确用户证据支撑的独立演进，
届时新增字段不会破坏本次契约（只增不改）。

**语义细化**：

- `DueDate` 可为 `null`，表示「未安排」。**这是默认状态**，不是缺失状态。
- `DueDate` 存储为**当日零点的日期值**，不携带有意义的时间部分。
  本工具不做「下午 3 点提醒」这类精确到时刻的调度（无提醒能力，见 §3.4）。
- 存储时区策略见 §5.3 —— 这是本文最容易埋雷的一处，单独讨论。

### 3.2 `Description`：保留，作为可选备注

**决策**：启用现有 `Description` 字段，定位为「任务的补充说明」，纯文本，无格式。

**为什么**：字段已在数据契约中存在（`TaskItem.cs:18`），且 design-visual-language 已向用户承诺。
当前它是一个「声明了但从未实现」的死字段 —— 要么实现它，要么删掉它，
不允许继续以死字段形式留存（Article 10）。选择实现，因为速记场景确实存在
「标题一句话记下，细节稍后补」的真实需求。

**边界**：

- 纯文本，不支持 Markdown / 富文本 / 附件。渲染成本与速记定位不匹配。
- 无长度硬限制，但 UI 上按多行文本框呈现，超长时滚动而非截断。
- 任务列表主视图**不展示** `Description` 全文，仅以一个轻量标记提示「此任务有备注」，
  避免破坏 Editorial 排版的呼吸感（spec-editorial-and-ripple-theme 已确立的视觉契约）。

### 3.3 优先级：保持三档不变

**决策**：`TaskPriority` 维持 `Low / Medium / High` 三档
（`src/FlowTask.Core/Enums/TaskPriority.cs`），不新增档位、不改变默认值 `Medium`。

**为什么**：三档已被现有 UI（P1/P2/P3 单选）与排序逻辑消费，运行正常，无改动动机。
无缘由地改动一个可用的契约本身就是风险。

### 3.4 本轮不引入的字段

| 候选 | 不引入的理由 |
| :--- | :--- |
| 标签 / Tags | 需要标签管理、重命名、合并、删除的完整生命周期，以及多对多存储。体量足以独立成篇，且当前任务量下筛选价值低于其复杂度成本（原则 3）。 |
| 清单 / 分组 / 项目 | 同上。且与「视图筛选」概念存在语义重叠，草率引入会重演 spec-editorial-and-ripple-theme 修正过的「设置页混入筛选枚举」类耦合。 |
| 提醒 / 通知 | 需要后台调度器与各平台通知权限，属于运行时能力而非数据模型问题。归入托盘常驻那一批（§1.4）。 |
| 重复任务 / 循环规则 | 循环规则（RRULE）是独立的复杂子领域，且必须先有稳定的单次任务模型作为基础。 |
| 子任务 / 父子层级 | 层级会波及所有查询、排序与删除级联逻辑。在扁平模型尚未打磨稳定前引入，收益低风险高。 |
| 排序权重 / 手动拖拽排序 | 当前排序由优先级 + 到期日决定，是确定性的。手动排序需引入持久化序号与重排算法，独立立项。 |

上述判断均为「**本轮不做**」，非「永不做」。不构成隐形债务
—— 它们是有理由的显式排除，不是被遗忘的待办（Article 4）。

### 3.5 契约变更汇总

`TaskItem` 的字段集合**不发生任何增删**。本次决策的实质是：
为已存在的 `DueDate` 与 `Description` 补齐读写路径与语义定义。

这是一个重要的结论：**本次设计不产生数据库迁移**。
现有 `flowtask.db` 中的既有数据在新逻辑下全部保持有效，
`DueDate`/`Description` 为 `NULL` 的历史任务自然落入「未安排 / 无备注」状态。

## 4. 决策二：编辑闭环

### 4.1 问题

任务一旦创建，标题永久无法修改。打错一个字只能删除重建，
且重建会丢失原 `CreatedAt`。这是比到期日缺失更基础的功能空洞。

### 4.2 决策：行内展开式编辑，不使用独立对话框

**决策**：点击任务行进入**就地展开**的编辑态，在同一位置展开出标题、备注、
到期日、优先级四项可编辑内容；再次点击或按 `Esc` 收起。

**为什么不用模态对话框**：
模态框会遮挡任务流、打断视线连续性，与 spec-editorial-and-ripple-theme 建立的 Editorial 沉浸式排版基调冲突。
design-visual-language 原提「双击查看备注」，但双击在触控板上的可发现性差，
且与勾选完成的单击存在误触竞争 —— 改为**点击任务行主体区域**展开，
勾选圈与删除按钮各自保留独立的点击热区，互不干扰。

### 4.3 保存语义：即时保存，无「取消」

**决策**：编辑态内的每一项变更在失焦或值变更时立即落库，不提供「保存 / 取消」按钮对。

**为什么**：本地 SQLite 写入是微秒级的（[adr-technology-stack](../adr/adr-technology-stack.md) §2），
不存在需要用户等待的提交成本。引入显式保存按钮反而带来「未保存状态」这一额外状态机，
以及「用户改了却忘记点保存」的数据丢失风险。

**代价与接受理由**：没有「取消」意味着误改无法一键还原。
考虑到编辑粒度极小（单行标题、一个日期），且撤销栈的引入成本远高于其收益，
本轮接受此代价。**明示排除**：不实现撤销 / 重做。

### 4.4 空标题的处理

**决策**：编辑时将标题清空并失焦，视为无效输入，**恢复为原标题**，不保存。

**为什么**：无标题任务在列表中不可识别，等同于数据垃圾。
现有创建路径已对空白标题静默忽略
（`MainViewModel.AddTaskAsync`、`QuickCaptureViewModel.SaveAsync`），
编辑路径必须保持一致，否则同一约束在两处出现不同行为（Article 6）。

### 4.5 随手记浮窗保持极简

**决策**：随手记浮窗**不引入**到期日与备注输入，维持「标题 + 优先级 + 回车」。

**为什么**：这是原则 1 的直接应用。随手记的唯一使命是零摩擦落库，
任何字段扩充都在损害其存在理由。补充信息应在主工作台的编辑态中完成。

**附带采纳**：`Shift+Enter` 连续记录（design-visual-language 已承诺未实现）
—— 保存当前条目但不关窗、清空输入等待下一条。
这是纯粹强化捕捉效率的能力，与极简定位一致。

## 5. 决策三：时间语义与 `IClock`

### 5.1 现存违规

`SqliteTaskRepository.GetTodayTasksAsync` 直接调用 `DateTime.Today`
（`src/FlowTask.Infrastructure/Persistence/SqliteTaskRepository.cs:68`），
业务查询分支依赖系统时钟，**违反 Article 9**。

后果不只是「不合规」：这使「今日」的边界不可测试 ——
无法编写「跨越午夜时任务是否正确移出今日视图」这类测试，
因为测试无法控制当前时间。

### 5.2 决策：引入 `IClock` 抽象

**决策**：在 `FlowTask.Core` 定义时钟抽象，由 `FlowTask.Infrastructure` 提供系统实现，
经构造注入到所有需要「现在」的组件。所有 `DateTime.UtcNow` / `DateTime.Today`
的直接调用点一并改为经此抽象获取。

**波及的现有调用点**（须全部改造，不得遗留混用）：

- `SqliteTaskRepository.GetTodayTasksAsync` —— 「今日」区间计算
- `TaskItem.CreatedAt` 默认值（`TaskItem.cs:26`）—— 实体自带 `DateTime.UtcNow` 初始化
- `MainViewModel.ToggleCompleteAsync` 的 `CompletedAt` 赋值（`MainViewModel.cs:286`）

> **注意 `TaskItem.CreatedAt` 的特殊性**：它是实体字段默认值，
> 实体无法被注入依赖。此处需在设计评审时确认取向 ——
> 是由创建方（ViewModel / 仓储）显式赋值，还是接受实体默认值作为 Article 9 的合理例外。
> **本文倾向前者**：由创建方赋值，实体默认值改为 `default`，
> 使「任务创建时间」成为一个被显式决定的业务事实而非隐式副作用。

### 5.3 时区：这是本设计最危险的一处

**现存缺陷**：`GetTodayTasksAsync` 计算「今日」的方式是
`DateTime.Today.ToUniversalTime()` 到 `+1 天`。这在**非 UTC 时区下是错的** ——
它取本地零点转为 UTC 时刻，再加 24 小时，得到的区间与用户心中的「今天」错位。

**决策**：

- **`CreatedAt` / `CompletedAt` 存 UTC**。它们是「事件发生的时刻」，
  UTC 是唯一无歧义的表示，且用户从不按这两者做日期筛选。
- **`DueDate` 存本地日期语义**。它回答的是「用户日历上的哪一天」，
  是一个**日期**而非**时刻**。若按 UTC 时刻存储，用户在 UTC+8 设定的「今天」
  在跨时区或夏令时变更后会漂移到前后一天 —— 这是同类应用最常见的用户可见 bug。
- 「今日」区间判断必须在**本地日期维度**上进行，由 `IClock` 提供当前本地日期。

**代价**：库内两类时间字段采用不同基准，是一处需要在代码注释中明确标注的
非对称设计。接受此不一致，因为它源于两者本质不同的语义
（时刻 vs 日历日），强行统一才是错误。

### 5.4 「今日聚焦」视图的定义

**决策**：「今日聚焦」= 到期日为今天**或已逾期**的未完成任务。

**为什么包含逾期**：若严格只显示今天，昨天到期而未完成的任务会**静默消失**
—— 它既不在「今日」也不显眼于「全部」，成为用户注意力的盲区。
这与该视图「今天需要优先解决的关键事项」的既有定位
（`MainViewModel.cs:151` 副标题文案）直接矛盾。

逾期任务在视图中需有明显的视觉区分（具体表现由实施阶段依 spec-editorial-and-ripple-theme 已建立的
令牌体系确定，本文不规定像素）。

## 6. 决策四：删除的最终状态

### 6.1 问题

`SoftDeleteAsync` 将 `IsDeleted` 置真，此后该记录：
在任何视图中都不可见，无恢复入口，永不被清理。
`PermanentDeleteAsync` 存在但无调用方。
结果是数据库只增不减，用户误删无法挽回。

### 6.2 决策：补「回收站」视图，保留期内可恢复

**决策**：

1. 新增第四个筛选视图「回收站」，列出 `IsDeleted` 为真的任务。
2. 回收站内每条任务提供「恢复」与「彻底删除」两个动作。
   「彻底删除」调用现有 `PermanentDeleteAsync`，此操作不可逆，须有确认。
3. 提供「清空回收站」批量动作，同样需确认。

**为什么不做自动过期清理**：
「保留 30 天后自动物理删除」听起来更完善，但它需要一个由时间驱动的后台清理任务
—— 引入调度器、启动时批量扫描、以及「删除时间」这个新字段。
这与 §3.4 排除提醒功能的理由一致：本轮不引入需要后台调度的能力。
**用户显式清空**在功能上等价，且完全可控、完全可测试。

### 6.3 恢复语义

**决策**：恢复即将 `IsDeleted` 置假，任务回到其原本应属的视图
（依 `IsCompleted` 决定回到活跃还是已完成）。
不保留「删除前所在视图」这类额外状态。
