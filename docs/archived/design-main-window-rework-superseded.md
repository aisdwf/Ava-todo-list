## 1. 现状问题诊断

经代码核实的具体成因，避免只描述症状（Article 2）：

### 1.1 顶部添加栏等同随手记

`MainViewModel.AddTaskAsync` 与 `QuickCaptureViewModel.SaveAsync`
调用完全一致 —— 均为 `TaskItemFactory.Create(clock, 标题, 优先级)`，
**均不传 `projectId`**。主窗口没有任何"大窗口该有"的能力。

### 1.2 项目上下文被丢弃

`SelectedProject` 在整个 `MainViewModel` 中**只被查询路径读取**
（`LoadTasksAsync` 一处），`AddTaskAsync` 完全未引用它。

后果链：在项目 A 视图下新建任务 → 落入「未归属」 →
当前列表只显示项目 A 的任务 → **新建的任务立即从视野消失** →
用户判定添加失败。

### 1.3 侧边栏存在两套并行的选中机制

| 区域 | 实现方式 |
| :--- | :--- |
| VIEWS 三项 | `RadioButton` + `IsChecked` 双向绑定 + `_isSyncingFilter` 抑制回环 |
| 项目行 | `Border` + `Tapped` 事件 + 手工维护 `IsSelected` 布尔量 |

二者的互斥靠在 `SelectProjectAsync` 与 `OnCurrentFilterChanged` 中
**手工清零对方**来维持。

**这是「新值等于旧值时回调不触发」缺陷的结构性土壤**：
spec-classification-ui 已修过一次（`ReturnToActiveViewAsync`），但结构未变，
同类缺陷仍会复现。这不是偶发失误，是双机制并存的必然产物。

### 1.4 编辑入口不可发现

「点击任务标题展开编辑」无任何视觉提示 —— 无图标、无悬停变化、
无「可展开」的形态暗示，仅有一个 `ToolTip`。

### 1.5 手工输入负担

| 字段 | 当前录入方式 |
| :--- | :--- |
| 标签 | 纯文本框，手输逗号分隔字符串 |
| deadline | 纯文本框，手输严格 `yyyy-MM-dd` |

`design-domain-contract §7.2` 曾把到期日输入方式列为「实现细节，可后定」，
实施时便退化为最省事的纯文本框。**把交互方式判定为实现细节是错误的** ——
它直接决定可用性。

### 1.6 完成任务后即时消失

`ToggleCompleteAsync` 完成后调用 `LoadTasksAsync`，
当前视图（全部/项目）均排除已完成项，任务立即从列表移除且无任何过渡与反馈。

## 2. 决策一：配置常驻，取消独立编辑态

**用户明示**：「就应该常驻配置的内容。需要配置的不多，并且保证一个合理的默认态，
完全足够保持轻量」「跳出弹窗完全违背设计原则」。

### 2.1 顶部创建区：常驻四项配置

顶部添加栏由「输入框 + 优先级三选」扩展为常驻以下控件：

```
＋ [标题输入框..................] [项目▾] [日期▾] [标签▾] [P1 P2 P3]
```

| 控件 | 默认态 | 说明 |
| :--- | :--- | :--- |
| 项目 | **当前上下文项目**（见 §3） | 非当前项目视图时默认「未归属」 |
| 日期 | **无**（未安排） | 点击展开日历 + 快捷预设，见 §5 |
| 标签 | **无** | 点击展开已有标签多选，见 §4 |
| 优先级 | P2（中） | 沿用现状 |

**合理默认态是轻量性的保障**：四项全部有合理默认值，
用户可以只输入标题按回车，行为与现在完全一致 ——
常驻控件不构成必填负担。

**明确排除**：模态对话框、独立编辑窗口、任何"跳出"式交互。

### 2.2 取消行内展开编辑态

**用户明示**：「不需要特别的编辑的，顶多像项目名称那样双击修改一下具体内容」。

spec-classification-ui 引入的 `EditPanel`（含五个字段的展开面板）**整体移除**。
理由：配置已在创建时常驻可用，事后修改由 §6.1 的双击原地编辑承担。

**[推断]** 已存在任务的项目/日期/标签如何修改？
本文倾向：任务行上的这些元素本身即为可点击的就地编辑入口
（点击色条改项目、点击日期改日期、点击标签区改标签），
与"双击标题改标题"形态一致，均为**就地**而非展开面板。
**推断依据**：用户否定的是"独立编辑态"，认可的是"像项目名称那样双击修改"，
即认可就地编辑这一形态。此项需评审确认。

## 3. 决策二：继承当前项目上下文

**用户明示**：「至于在项目 a 新建就归于项目 a，这是基本直觉，也应该保留」。

### 3.1 规则

新建任务的项目归属默认取当前视图上下文：

| 当前视图 | 新任务默认项目 |
| :--- | :--- |
| 项目 A | **项目 A** |
| 全部任务 | 未归属 |
| 已归档 | 未归属 |

用户可在创建前通过顶部的项目选择器改变该默认值。

### 3.2 随手记浮窗不继承

**[推断]** 随手记浮窗创建的任务归属「未归属」，不继承主窗口的当前项目。
**推断依据**：小窗的使命是脱离当前上下文的快速捕捉，
且主窗口可能不在前台、其"当前项目"对用户不可见 ——
继承一个看不见的上下文会产生意外归属。此项需评审确认。

## 4. 决策三：标签的选择与管理

**用户明示**：「可以手动配置并选择标签，有单独的管理设计，
并应该根据实际 ui 情况给出上限或者需要展开的界面能力」。

### 4.1 录入：选择优先，允许新建

顶部标签选择器点击后展开面板：

- **已有标签多选列表** —— 从现存任务中提取去重（`GetAllTagsAsync` 已实现）
- **新建标签输入框** —— 仅在需要新标签时使用

这消除了「每次都手输、拼写不一致产生近似重复标签」的问题。

### 4.2 数量上限

**用户要求**「根据实际 ui 情况给出上限或者需要展开的界面能力」。

**[推断]** 单任务标签数上限 **5 个**；任务行仅显示前 **2 个**，
其余以 `+N` 折叠，悬停或点击展开全部。
**推断依据**：任务行需为标题保留主要横向空间（Editorial 排版基调），
实测 1180px 窗宽下超过 2 个标签会明显压缩标题区。
具体数值需在实施时依实际渲染效果微调，此处为待确认的初值。

### 4.3 标签管理界面

**用户明示**要求「单独的管理设计」。管理能力应包含：

- 列出全部在用标签及其使用计数
- **重命名**（批量更新所有引用该标签的任务）
- **删除**（从所有任务移除该标签）
- 合并（两个近似标签归一）

> **⚠ 契约影响，须评审确认**：
> design-domain-contract §4.3 决定标签以**分隔符拼接字符串**存储，
> 其明示接受的代价正是「**无法重命名标签**」。
>
> 现要求提供重命名与合并，该代价不再可接受。两条路：
>
> | 方案 | 做法 | 代价 |
> | :--- | :--- | :--- |
> | A. 保留字符串存储 | 重命名时全表扫描 + 逐条字符串替换 | 实现简单；但非原子操作，中途失败会留下部分改名的脏数据；任务量大时慢 |
> | B. 升级为独立实体 | `Tag` 表 + `TaskTag` 关联表 | 重命名是单行 UPDATE，天然原子；但 `sqlite-net-pcl` **无关系映射能力**（已实测确认），全部 JOIN 与组装需手写 |
>
> **✅ 已裁决（2026-09-15）：采用方案 B —— 标签升级为独立实体表。**
>
> 用户原话：「b，我对标签的理解就是提供可删除的预设，并且支持自己定义一些（设置页面）。
> 后续直接选择标签，而不是手动输入。」
>
> 判据一致性：一旦标签需要重命名、删除、合并这套治理能力，
> 它的职责已与「项目」同级 —— design-domain-contract §4.2 正是以
> 「需要重命名故值得独立实体」判定项目该建表。
> 同样判据应得同样结论。

### 4.3.1 标签的完整定位（用户明示后细化）

用户原话拆解出三条硬要求：

| 用户表述 | 设计含义 |
| :--- | :--- |
| 「提供可删除的**预设**」 | 应用**内置一批开箱可用的标签**，且用户可删除不需要的 |
| 「支持自己定义一些（**设置页面**）」 | 新建标签的入口在**设置页**，不在任务创建流程中 |
| 「后续**直接选择**标签，而不是手动输入」 | 任务创建/编辑时**只能选**，**不提供**自由文本输入 |

**这是与 design-domain-contract §4.3 的根本差异**：那里把标签当作「随手输入即创建」的轻量标记，
现在标签是**受管理的预定义集合**。

**[推断]** 内置预设标签的候选集：
`紧急`、`重要`、`日常`、`学习`、`工作`、`个人`、`待确认`、`已阻塞`。
**推断依据**：需覆盖通用待办场景且数量克制（用户说「需要配置的不多」）。
**此项需评审确认**，尤其是是否要内置、以及具体词条。

### 4.3.2 严禁强制手动输入（全局约束）

**用户明示**：「todolist 不需要给自己加 note，这些配置严禁出现强制依赖手动输入的内容。」

这是一条**适用于全部配置项**的硬约束，不只针对标签：

| 配置项 | 录入方式 | 是否含手动输入 |
| :--- | :--- | :--- |
| 项目 | 下拉选择（继承上下文为默认） | 无 |
| 标签 | 多选（从预设集合） | 无 |
| deadline | 快捷预设 / 日历点选 / 纯数字快速输入 | 数字输入是**可选加速路径**，非唯一手段 |
| 优先级 | 三选按钮 | 无 |
| 标题 | 文本输入 | **唯一允许**的手动输入 |

**推论：`Description`（备注）字段应正式废弃。**
用户明示「todolist 不需要给自己加 note」。
该字段自 spec-mvvm-infrastructure 起就是死字段，历经 spec-task-contract-and-clock / spec-classification-ui 两次登记推迟。
现在有了明确的产品决策依据 —— 它不该被启用，而应被移除。
**需评审确认是否物理删除该列**（涉及数据契约变更）。

### 4.4 管理入口

**用户明示**：「设置可以有单独的配置，并且在左边添加设置的具体选项，
添加了设置功能当然不会只针对外观」。

即：左侧边栏应有**设置区**，其下含多个具体选项，而非仅「外观」一项。
标签管理归入此处。详见 §6.3。

## 5. 决策四：deadline 的双来源输入

**用户明示**：「deadline 需要预设默认，并且采用日历控件，
顶部也支持快速输入年月日，只需要数字即可」
「使用日历挂件也应该同步输入在结果，也就是双来源同步」。

### 5.1 三种录入方式并存

| 方式 | 形态 | 说明 |
| :--- | :--- | :--- |
| **快捷预设** | 按钮组 | 今天 / 明天 / 本周末 / 下周 / 清除 |
| **日历控件** | `Calendar` | 点选具体日期 |
| **数字快速输入** | 文本框 | 只输数字，无需分隔符 |

### 5.2 双来源同步

三者操作**同一个日期值**，任一处变更立即反映到其余两处：

- 日历点选 3 月 10 日 → 数字输入框显示 `0310`，快捷预设高亮「今天」（若恰为今天）
- 数字框输入 `0310` → 日历跳转并选中该日
- 点「明天」 → 日历与数字框同步

**[推断]** 数字输入的解析规则：
| 输入 | 解析为 |
| :--- | :--- |
| `10` | 本月 10 日 |
| `0310` | 今年 3 月 10 日 |
| `260310` | 2026 年 3 月 10 日 |
| `20260310` | 2026 年 3 月 10 日 |

**推断依据**：用户要求「只需要数字即可」，未指定位数规则。
上表按「位数越少、省略的是越高位」这一通用直觉设计。
需评审确认，尤其是 2 位与 6 位的处理。

**[推断]** 解析失败时不清除已有值，保留原日期并给出轻量提示，
而非当前实现的「非法即视为清除」—— 后者会静默丢失用户已设的日期。

## 6. 决策五：侧边栏重构

**用户明示**：「侧边栏就是全部、归档、以及可能某个具体的项目框，
感觉完全感受不到变化」「一是重复，二是寻找困难」
「目前的管理方式还是不够优雅」。

### 6.1 就地编辑

**用户明示**：「顶多像项目名称那样双击修改一下具体内容」。

任务标题双击进入原地编辑，Enter 提交、Esc 取消、失焦保存 ——
与项目重命名的交互完全一致（该交互用户已认可）。

### 6.2 消除重复与寻找困难

用户指出两个具体问题：**重复**、**寻找困难**。

**重复的来源**：「全部任务」与「某个项目」在内容上高度重叠 ——
项目下的任务同时出现在「全部任务」中，两处看到的是同一批数据的不同切片，
但侧边栏把它们呈现为并列的同级入口，用户感受不到切换的意义
（「感觉完全感受不到变化」）。

**[推断]** 可能的改造方向（需评审选择）：

| 方案 | 做法 | 权衡 |
| :--- | :--- | :--- |
| A. 层级化 | 「全部任务」作为根，项目作为其下的子筛选（缩进呈现） | 表达了包含关系，消除同级并列的错觉；但增加视觉层级 |
| B. 分组标题化 | 项目区不作为可选中项，改为「全部任务」列表内的分组标题 | 最轻量，一屏看全；但失去"只看某项目"的聚焦能力 |
| C. 保持并列但强化差异 | 项目视图显示项目专属信息（进度、描述） | 改动最小；但未触及"重复"的根本 |

**本文不预设倾向** —— 这是纯粹的信息架构取舍，
且用户已明确表达「看似合理但操作难受」，说明纸面推理不足以判断。
建议评审时结合实际界面讨论。

### 6.3 设置区

**用户明示**：「在左边添加设置的具体选项，添加了设置功能当然不会只针对外观」。

侧边栏底部增设设置区，其下为具体选项而非单一入口：

```
SETTINGS
  外观          ← 现有（主题/材质/强调色）
  标签管理      ← 新增（§4.3）
  项目管理      ← 新增（含归档，补齐 spec-classification-ui 的推迟事项 登记的缺失）
```

> **顺带核销一项已登记待办**：spec-classification-ui 的推迟事项 记录「项目归档命令已实现但无 UI 入口」，
> 原因是项目行已有 3 个操作、侧边栏塞不下第 4 个。
> 移入设置区的项目管理后，归档有了合理承载位置。

**[推断]** 设置区采用可折叠形态，默认收起，避免与 VIEWS / PROJECTS 争夺视觉重心。

### 6.4 完成任务后不即时消失

**用户明示**：「我点了某个任务完成，瞬间就去了已归档，找都找不到。
这也是 design 上的失误」。

**[推断]** 可能的处理方式（需评审选择）：

| 方案 | 做法 | 权衡 |
| :--- | :--- | :--- |
| A. 延迟移除 | 勾选后保留 2~3 秒（划线置灰）再移出列表 | 有明确的完成反馈；但延迟期间再次勾选的语义需定义 |
| B. 就地保留 | 已完成项留在当前列表底部（划线置灰），刷新视图才移出 | 可立即撤销误勾；但列表会逐渐混入已完成项 |
| C. 完成后提示可撤销 | 移除的同时显示「已完成 XX · 撤销」轻量提示条 | 反馈明确且可挽回；需引入提示条组件 |

**本文倾向 B + C 组合**：就地保留提供即时可见性，
配合轻量提示告知「已归入已完成」，解决"找都找不到"。
**推断依据**：用户的抱怨核心是「找不到」而非「消失太快」，
故重点应是**保持可见**与**告知去向**，而非仅延长动画时间。
需评审确认。

## 7. 结构性整改（与交互决策独立）

### 7.1 侧边栏选中机制收敛为一套

§1.3 诊断的双机制并存是技术债，**无论 §6.2 选择哪个方案都应整改**。

该模式已在本项目出现两次（spec-editorial-and-ripple-theme 导航无响应、spec-classification-ui 高亮空档）。

### 7.2 建议沉淀为项目规则

**[推断]** 「依赖属性变更回调同步状态，在新值等于旧值时必然失效」
已两次致缺陷，符合规则化门槛，建议立 rule-spec-review-gate。
依 `docs/rules/README.md` 的事故驱动原则，两次同类事故应转为机器可检查的规则。
