## 1. 最高原则：轻量由默认态保障，而非由功能缺失保障

这是本项目交互设计的**首要判据**，当其他原则冲突时以此裁决。

**含义**：配置项可以常驻在界面上，只要每一项都有**合理的默认值**，
用户就能忽略它们、只输入标题即完成操作。

**反面教材**（曾经的错误做法）：为了「保持简洁」而不提供配置入口，
迫使用户先创建、再逐个补配置。这不是简洁，是功能缺失。

---

## 2. 配置常驻，严禁弹窗

### 2.1 常驻

需要配置的项目不多，全部常驻在主操作路径上。
用户看得见即知道能配，无需探索。

### 2.2 严禁跳出式交互

**明确排除**：模态对话框、独立配置窗口、任何"跳出"式交互。

弹窗会遮挡内容、打断视线连续性，与沉浸式排版基调冲突。

### 2.3 可发现性是硬要求

配置入口必须**自身可见**，不得依赖用户猜测。

**反面教材**：曾把编辑入口做成「点击任务标题展开」，
无图标、无悬停提示、无形态暗示，仅有一个 ToolTip ——
用户反馈「根本没有发现这个 list 是可以点开配置的」。

---

## 3. 继承当前上下文

新建任务的默认归属取自**当前视图上下文**：

| 当前视图 | 新任务默认项目 |
| :--- | :--- |
| 某个项目 | **该项目** |
| Default 项目 / 已归档 | **Default 项目** |

用户可在创建前通过常驻的项目选择器改变该默认值。

**为什么这是硬要求**：用户已经在某个项目视图里，
这是**最强的意图信号**。忽略它会导致新建的任务落入错误项目，
而当前列表只显示该项目的任务 —— **任务立即从视野消失，用户判定添加失败**。

**用户裁决（2026-09-16）**：取消「全部 / 未归属」切片，改为系统 **Default 项目**。
不想填项目时任务落入 Default，既零摩擦又保持 base-on-project。

**小窗**：不继承主窗口当前项目；无 `@项目` 或 `@` 未匹配时落入 **Default**
（未知 `@`/`#` **不自动创建**，未匹配片段留在标题）。

---

## 4. 严禁强制手动输入

**除标题外，任何配置项都必须提供非手输的录入方式。**

### 4.1 录入方式对照

| 配置项 | 录入方式 |
| :--- | :--- |
| 标题 | 文本输入（**唯一允许**） |
| 项目 | 下拉选择 |
| 标签 | 多选 |
| deadline | 快捷预设 / 日历 / 纯数字加速输入 |
| 优先级 | 三选按钮 |

### 4.2 标签只选不输

标签是**受管理的预设集合**（字段语义见
[design-domain-contract](./design-domain-contract.md) §4.3）：

- 应用内置一批可删除的预设；
- 用户可在**设置页**自定义新增；
- 任务侧**只能选择**，严禁自由文本输入。

**为什么**：手输标签导致拼写不一致、产生大量近似重复标签，
用户评价其对后续维护是「灾难级」的。

### 4.3 deadline 三来源同步

三种录入方式**并存且操作同一个日期值**，任一处变更立即反映到其余两处
（用户称之为「双来源同步」）：

| 方式 | 形态 |
| :--- | :--- |
| 快捷预设 | 今天 / 明天 / 本周末 / 下周 / 清除 |
| 日历控件 | 点选具体日期 |
| 数字快速输入 | 只输数字，无需分隔符 |

**为什么必须如此**：曾要求用户手输严格的 `yyyy-MM-dd` 格式，
用户评价「谁会没事干完整地看一遍年月日并按照你要求的格式完整输入一遍，
没有输错的风险吗」。

**[推断]** 数字输入的位数解析：`10` → 本月 10 日；
`0310` → 今年 3 月 10 日；`260310` / `20260310` → 2026 年 3 月 10 日。
**推断依据**：用户要求「只需要数字即可」但未指定位数规则，
上表按「位数越少、省略的是越高位」这一通用直觉设计。

**[推断]** 解析失败时**保留原值**并轻量提示，
而非「非法即视为清除」—— 后者会静默丢失用户已设的日期。

## 5. 就地编辑，不设独立编辑态

**用户明示**：「不需要特别的编辑的，顶多像项目名称那样双击修改一下具体内容。」

- 任务标题：双击进入原地编辑，Enter 提交、Esc 取消、失焦保存；
- 与项目重命名的交互**完全一致**（该交互已被用户认可）。

**排除**：含多字段的展开式编辑面板。
配置已在创建时常驻可用，事后修改由就地编辑承担。

**[推断]** 已存在任务的项目 / 日期 / 标签修改，
由任务行上的对应元素本身作为就地编辑入口
（点击色条改项目、点击日期改日期、点击标签区改标签）。
**推断依据**：用户否定的是"独立编辑态"，认可的是"就地修改"这一形态。

---

## 6. 双窗口的功能分工

**用户明示**：「大窗口就要有大窗口的功能。」

| 视窗 | 功能定位 |
| :--- | :--- |
| **主工作台** | 任务全生命周期管理：分类、配置、编辑、批量整理 |
| **随手记浮窗** | 极速捕捉 + 日常快速勾选查看（见 §8） |

**严禁**让主窗口的创建路径退化为随手记的复制品 ——
二者若能力等同，主窗口就失去了存在意义。

---

## 7. 侧边栏

### 7.1 结构

侧边栏承载：全部任务、已归档、各具体项目、以及设置区。

**设置区含多个具体选项，不止外观**（用户明示
「添加了设置功能当然不会只针对外观」）：外观、标签管理、项目管理（含归档）。

### 7.2 避免重复与寻找困难

用户指出两个具体问题：「一是重复，二是寻找困难」
「看似合理但是操作难受」「实际由于糟糕的设计，体验还不如完全轻量化」。

**重复的来源**：「全部任务」与「某个项目」在内容上高度重叠 ——
项目下的任务同时出现在「全部任务」中，两处是同一批数据的不同切片，
但侧边栏把它们呈现为**并列的同级入口**，用户感受不到切换的意义。

**信息架构的具体方案属待裁决事项**，不在本文预设 ——
用户已明确表示纸面推理不足以判断，需结合实际界面讨论。
候选方案与权衡见 [spec-sidebar-selection-consolidation](../specs/main-window/spec-sidebar-selection-consolidation[DONE].md)。

### 7.3 完成任务后必须可追溯

**用户明示**：「我点了某个任务完成，瞬间就去了已归档，找都找不到。
这也是 design 上的失误。」

**用户补充（2026-09-16）**：勾选后不应立刻消失，应先呈现归档视图同款的
划线低饱和「已完成」态；**归档须用户手动触发**
（例如「完整归档项目」类操作），以便误触时可就地取消勾选回退。

原则：

1. **完成 ≠ 归档**（需求 R-4.1～R-4.3）；
2. 完成操作必须给出**明确反馈**，任务在归档前仍留在活动列表；
3. 取消勾选即可回退，无需进入归档视图。

具体字段与归档入口见
[spec-task-complete-before-archive](../specs/task-domain/spec-task-complete-before-archive[DRAFT].md)。

### 7.4 零分类状态必须是完整体验

若用户从不使用项目与标签，体验应与不存在这些功能时**完全一致**：

- 无项目时，侧边栏项目区**整块隐藏**（不显示空列表、不显示占位）；
- 任务行无分类信息时，布局与不含这些元素时一致；
- 各元素独立控制显隐，而非预留空位。

## 8. 随手记浮窗

**用户明示**：「小窗我认为应该聚焦两个功能：
日常可以做 todolist 的快速打勾和查看的操作，也支持快捷键快速添加的功能。」

| 能力 | 要求 |
| :--- | :--- |
| 查看 | 展示当前待处理任务列表 |
| 快速勾选 | 无需打开主窗口即可标记完成 |
| 快捷添加 | 保留现有输入能力 |
| 全键盘可达 | 呼出、浏览、勾选、添加、关闭均有键盘路径 |

**排除**：小窗不引入独立的项目/标签/日期**配置面板** ——
补充信息的主战场仍在主工作台。

**用户补充（2026-09-16）**（部分推翻「输入侧零分类」）：

- 小窗输入支持 **`@项目` `#标签`** 行内语法，并最好有补全；
- 列表初版为**单项目**，并**记忆上次项目**；
- 以快捷键**显示/隐藏**小窗；Windows 要求近似全局，macOS 需核实前台限制。

**[推断]** 小窗任务行只显示勾选圈、标题；单项目上下文下项目色条可省略。
**推断依据**：小窗职责是「快速打勾和查看」而非「审阅任务全貌」。

## 9. 渐进披露

高级能力不占用主路径，仅在用户主动进入时展开：

- 项目管理（增删改归档）不占主界面空间，收纳于设置区；
- 新建项目入口默认仅一个「＋」，点击才展开输入；
- 简洁性由「默认不可见」保障，而非由「功能不存在」保障。

## 10. 历史沿革

本文的原则来自一次**设计返工**。早期的主窗口交互设计
（原 design-domain-contract §5 / §4.2 / §5）由撰写者自行推理产出，
未经用户验证即实现，交付后被实测推翻。

被推翻的判断包括：「分类应在创建后补充」（忽略上下文意图）、
「主输入路径不新增控件」（把功能缺失当简洁）、
「标签手输 + 自动补全即可」、「点击行展开编辑」。

**根因已沉淀为规则**：
[rule-no-invented-user-behavior](../rules/rule-no-invented-user-behavior.md)。

原文档的失效部分见
[`archived/design-task-classification-superseded.md`](../archived/design-task-classification-superseded.md)。
