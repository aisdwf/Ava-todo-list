## 1. 存储技术约束

**已实测确认的两条边界**（非推断，验证方式见
[spec-task-contract-and-clock](../specs/task-domain/spec-task-contract-and-clock[DONE].md)）：

### 1.1 新增列无需迁移脚本

`sqlite-net-pcl` 1.9.172 的 `CreateTable` 对已存在的表新增列时，
自动执行 `ALTER TABLE ADD COLUMN`，返回 `CreateTableResult.Migrated`，
**既有行数据完整保留，新列取默认值**。

实测输出：

```
V1 建表并写入 1 行。行数 = 1
V2 CreateTable 返回：Migrated
V2 读取行数 = 1
  Id=abc Title=既有任务 Priority=2 ProjectId=NULL SortOrder=0
物理列：Id, Title, Priority, ProjectId, SortOrder
```

该结论已固化为回归测试（`SchemaMigrationTests`），
防止日后升级依赖时行为变化而无人察觉。

### 1.2 无关系映射能力

`sqlite-net-pcl` **无 `OneToMany` / `ManyToMany` / `GetChildren`**
（全库仅一个 `CollationAttribute`）。
因此**所有关联查询与组装必须手写**，不存在导航属性。

## 2. 任务（TaskItem）

### 2.1 字段语义

| 字段 | 类型 | 语义 |
| :--- | :--- | :--- |
| `Id` | `string` | 主键，GUID |
| `Title` | `string` | 标题。**唯一允许手动输入的字段**（见 §5） |
| `IsCompleted` | `bool` | 完成状态 |
| `Priority` | `TaskPriority` | 三档：`Low` / `Medium` / `High`，默认 `Medium` |
| `ProjectId` | `string` | 所属项目；**必有**。无显式选择时为系统 **Default** 项目（2026-09-16 裁决；废除 `null`=未归属） |
| `DueDate` | `DateTime?` | 到期日（**日历日**语义，见 §3） |
| `CreatedAt` | `DateTime` | 创建时刻（**UTC**，见 §3） |
| `CompletedAt` | `DateTime?` | 完成时刻（**UTC**） |
| `IsDeleted` | `bool` | 软删除标记 |
| `Description` | `string?` | **已废弃**，见 §2.4 |

### 2.2 不变量

以下不变量由仓储层（唯一写入漏斗）统一维护，
**不依赖各 UI 入口自觉遵守**：

1. `CreatedAt` 必须已被显式赋值（不得为 `default`），违反则快速失败；
2. `Title` 必须通过校验（非空 + 长度上限），违反则拒绝写入；
3. `DueDate` 归一化为当日零点、Kind 为 `Unspecified`；
4. ~~标签名称经 `TagName` 规范化；任务标签通过 `TaskTags` 关联表维护。~~
   **[已随标签移除废弃]**（2026-09-24）标签功能已完全移除，见 §4.3。

### 2.3 可空字段与 Default 项目

`DueDate` 为 `null` 表示「未安排」，**是完全正常的默认状态**。
UI **严禁**对其做视觉标记、警告或催促补全。

`ProjectId` **不可为 null**（2026-09-16）：以系统种子项目 **Default** 承接「不想填」。
历史 `ProjectId IS NULL` 须迁移到 Default。删除用户项目时，其下任务改挂 Default（不再置 null）。

### 2.4 `Description` 已废弃

**用户明示**：「todolist 不需要给自己加 note，
这些配置严禁出现强制依赖手动输入的内容。」

该字段自项目初期即为死字段（从未有 UI 读写路径），
历经两次「推迟启用」登记。现有明确的产品决策依据：**它不该被启用**。

处置：保留数据库列但永久停止使用。
**不物理删列** —— `sqlite-net-pcl` 删列需重建表，风险高于收益。

## 3. 时间语义（关键）

### 3.1 「时刻」与「日历日」是两种不同的类型

这是本项目**最容易出错**的一处，曾产生真实缺陷。两类时间值基准不同：

| 类别 | 含义 | 字段 | 存储基准 |
| :--- | :--- | :--- | :--- |
| **时刻（instant）** | 事件在哪一瞬间发生 | `CreatedAt` `CompletedAt` | **UTC** |
| **日历日（calendar date）** | 用户日历上的哪一天 | `DueDate` | **本地日期**（当日零点，Kind `Unspecified`） |

### 3.2 为什么不统一为 UTC

`DueDate` 回答的是「用户日历上的哪一天」。
若按 UTC 时刻存储，用户在 UTC+8 设定的「今天」在跨时区或夏令时变更后
会**漂移到前后一天** —— 这是同类应用最常见的用户可见缺陷。

**推论：修正时区问题的正确方向是「减少换算」而非「增加换算」。**
`DueDate` 全程不做任何时区转换，因为任何转换都会破坏「哪一天」这一语义。

### 3.3 时钟必须可注入

业务逻辑**严禁**直接读取 `DateTime.Now` / `DateTime.Today`
（[AI_CONSTITUTION](../../AI_CONSTITUTION.md) Article 9）。

统一经 `IClock` 抽象获取，该接口同时暴露两个语义分明的成员：

- `UtcNow` —— 时刻
- `Today` —— 本地日历日

**把两者放在同一接口并区分命名**，使调用方在选择成员时
就被迫明确自己要的是哪种语义，而非事后才发现基准错配。

唯一允许触达系统时钟的位置是 `SystemClock` 实现。

### 3.4 「今日聚焦」的定义

**今日 = 到期日为今天 _或已逾期_ 的未完成任务。**

**为什么包含逾期**：若严格只取今天，昨天到期而未完成的任务会静默消失 ——
既不在「今日」也不显眼于「全部」，成为注意力盲区。

判断在**本地日历日维度**进行：`DueDate < clock.Today.AddDays(1)`，
全程无时区换算。

## 4. 项目与标签

### 4.1 项目是独立实体

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `Id` | `string` | 主键 |
| `Name` | `string` | 可重命名，长度上限 50（由侧边栏 272px 宽度反推） |
| `ColorHex` | `string` | 项目色，用于任务行色条 |
| `SortOrder` | `int` | 侧边栏排列顺序 |
| `IsArchived` | `bool` | 归档标记 |
| `CreatedAt` | `DateTime` | 创建时刻（UTC） |

**为什么值得独立实体**：项目需要重命名（改一次、全部关联任务同步生效）、
颜色标识、排序与归档。这些都要求它拥有独立身份。
若退化为字符串标记，重命名将变成「批量查找替换」。

**一个任务只能属于一个项目**（「项目」一词的通用预期）。

### 4.2 归档与删除语义不同

| 操作 | 语义 | 对其下任务的影响 |
| :--- | :--- | :--- |
| **归档项目** | 项目不再活跃，历史归属有保留价值 | 任务保留，`ProjectId` **不变** |
| **归档已完成任务** | 将某项目下已完成项移入归档视图（2026-09-16） | 任务 `IsArchived=true`，**保留 `ProjectId`**（不是拆掉项目来源） |
| **删除项目** | 项目建错或不再需要 | 任务**保留**，`ProjectId` 改挂 **Default**（不可 null） |

**核心不变量：删除项目绝不删除其下任务。**
任务是用户的核心资产，项目只是它的一个可选属性 ——
删除属性不应销毁拥有该属性的实体。

实现要求：以**单个事务**完成「置空关联任务的 `ProjectId`」
与「删除项目行」，避免中途失败留下悬空外键。

> **注意**：`RunInTransactionAsync` 的回调签名是 `Action<SQLiteConnection>`
> —— 传入**同步**连接。回调内误用异步 API 会脱离事务边界，
> **原子性静默失效且不报错**。

**项目本身无软删除标记** —— 那会引出「项目回收站」，
而任务不被销毁已消除删除操作的主要风险。

### 4.3 标签：受管理的预设集合（已废弃）

> **⚠ 本节已废弃（2026-09-24）**：标签功能（`Tag`/`TaskTag` 实体及全部关联代码）
> 已被用户裁决完全移除（原话：「标签实际体验下来功能很累赘，可以考虑清理这个功能」），
> 详见 [spec-remove-tag-feature](../specs/task-domain/spec-remove-tag-feature[IN-PROGRESS].md)。
> 以下原文保留作历史记录（说明当时为何要实体化），**不再是当前数据契约**。

**用户明示（历史记录）**：「我对标签的理解就是提供可删除的预设，
并且支持自己定义一些（设置页面）。后续直接选择标签，而不是手动输入。」

**目标形态**：

| 表 | 字段 |
| :--- | :--- |
| `Tag` | `Id` / `Name`（唯一，大小写不敏感）/ `ColorHex` / `SortOrder` / `IsBuiltIn` / `CreatedAt` |
| `TaskTag` | `Id` / `TaskId` / `TagId`（多对多关联） |

**定位要点**：

- 标签是**受管理的预定义集合**，不是「随手输入即创建」的轻量标记；
- 应用内置一批开箱可用标签，且用户**可删除**；
- 新建标签入口在**设置页**，不在任务创建流程中；
- 任务侧**只能选择**，严禁自由文本输入。

**为什么必须实体化**：一旦标签需要重命名、删除、合并这套治理能力，
其职责已与「项目」同级 —— §4.1 正是以「需要重命名故值得独立实体」
判定项目该建表。同样判据应得同样结论。

本项目直接采用实体关联模型，不保留逗号分隔字符串字段或兼容读写路径。
标签名称、颜色与关联关系分别由各自的实体和仓储维护。

## 5. 全局约束：严禁强制手动输入

**用户明示**：「这些配置严禁出现强制依赖手动输入的内容。」

| 配置项 | 录入方式 | 含手动输入？ |
| :--- | :--- | :--- |
| 标题 | 文本输入 | **是（唯一允许）** |
| 项目 | 下拉选择（默认继承当前上下文） | 无 |
| 标签 | 多选（从预设集合） | 无 |
| deadline | 快捷预设 / 日历点选 / 纯数字快速输入 | 数字输入为**可选加速路径**，非唯一手段 |
| 优先级 | 三选按钮 | 无 |

此约束是**契约级**的：任何新增配置项都必须提供非手输的录入方式。

## 6. 校验规则真源

各字段的校验规则集中定义，**严禁**在各调用点自行判空或另定上限
（[AI_CONSTITUTION](../../AI_CONSTITUTION.md) Article 6）：

| 值对象 | 规则 |
| :--- | :--- |
| `TaskTitle` | Trim + 非空 + 上限 200。`Normalize` **只修剪首尾**，内部字符原样保留 |
| `ProjectName` | Trim + 非空 + 上限 50。`Normalize` **折叠内部空白** |

**两者 `Normalize` 刻意不同**：

- 任务标题内部字符须保留 —— 小窗输入语法为 **`@项目` / `#标签`**
  （2026-09-16 用户裁决；废弃早期预留的 `#项目` / `@标签` 前缀），
  依赖 `#` `@` 不被 `Normalize` 提前剥离；
- 项目名是被反复引用的标识符 —— 「我的 项目」与「我的  项目」视觉无法区分
  却会被当作两个不同项目。

校验兜底放在**仓储层**（唯一写入漏斗），而非仅 UI 层。
