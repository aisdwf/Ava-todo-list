## 1. 项目性质与质量标准

**性质**：快速掌握 Avalonia 的**学习项目**。

**但执行标准不降低**。学习项目在此仅意味着：
不承担商业交付压力、不需要用户增长考量、不做市场竞争分析。
它**不意味着**可以接受劣质工程实践。本项目仍严格受
[AI_CONSTITUTION](../../AI_CONSTITUTION.md) 十条约束，
代码质量、文档同步、验证闭环一律按可交付标准执行。

**这一定性的实际影响**：

- 技术选择优先考虑**是否有助于掌握 Avalonia 的关键能力**（自定义控件、样式系统、动画、多窗口、平台集成），
  在功能价值相近时，倾向能带来更多框架实践的方案；
- 不做面向陌生用户的运营性投入：无引导教程、无遥测、无崩溃上报、无自动更新；
- 但**基础可用性不打折**：数据不能丢、界面不能崩、操作要有反馈。

## 2. 目标用户

**主要用户：项目作者本人及具有同类习惯的开发者。**

有效的用户特征（能推导功能的部分）：

- 在键盘上工作，鼠标是次选。快捷键不是加分项而是基本预期；
- 待办产生于工作流中途（写代码时想起某事），**打断成本敏感**；
- 同时推进多个项目/方向，需要按项目归类而非单一扁平列表；
- 能接受本地单机、无同步。

**明确不作为目标**：非技术用户、团队协作场景、移动端用户。

> **反例警示**：早期 `README.md` 使用「高效思考者」描述目标用户。
> 此类表述不排除任何人，因而不构成任何约束，不可作为需求依据。

## 3. 产品定位与差异化立足点

### 3.1 立足点：随手记小窗

**这是本项目的核心特征，是最重要的产品决策。**

主窗口做的事（列表、分类、编辑）任何待办应用都有，不构成特色。
**小窗是唯一的差异化载体**，因此：

- 凡涉及小窗的能力，优先级高于主窗口的同类能力；
- 小窗的交互摩擦是最高优先级的缺陷类别；
- 当小窗与主窗口的设计取舍冲突时，**优先保障小窗体验**。

### 3.2 「通用一点」的含义

用户要求产品做得通用，即：

- **不为单一个人的特殊习惯做硬编码**。功能应服务于普遍的待办管理需求，
  而非只解决作者当下某个具体场景；
- 数据模型与交互应符合待办类应用的**通用预期**，
  使任何用过同类工具的人都能直接上手，无需学习；
- 但通用**不等于大而全**。见 §6 非目标。

## 4. 核心需求

### 4.1 小窗：聚焦两件事

**用户原话**：「小窗我认为应该聚焦两个功能：日常可以做 todolist 的快速打勾和查看的操作，也支持快捷键快速添加的功能。」

> **需求变更提示**：这**推翻了** design-domain-contract §4.5 的假设。
> 该处曾断定「小窗只负责零摩擦落库，维持标题+优先级+回车」，
> 并据此排除小窗的任何列表能力。现明确：小窗必须能查看和勾选任务。
> 当前 `QuickCaptureWindow` 是一个 620×150 的纯输入胶囊，无列表区域，
> 需要结构性改造而非增量调整。

| ID | 需求 | 说明 |
| :--- | :--- | :--- |
| R-1.1 | 小窗可**查看**任务列表 | 不只是输入框。需展示当前待处理任务 |
| R-1.2 | 小窗可**快速勾选完成** | 无需打开主窗口即可标记完成 |
| R-1.3 | 小窗可**快捷键快速添加** | 保留现有输入能力，键盘全程可达 |
| R-1.4 | 小窗全程**无需鼠标** | 呼出、浏览、勾选、添加、关闭均有键盘路径 |
| R-1.5 | **近似全局**快捷键显示/隐藏小窗 | **Windows 为验收重点**（进程已启动时无需主窗前台）。macOS 尽力而为；若受系统前台策略限制须文档化边界 |
| R-1.6 | 小窗输入支持 `@项目` 并补全 | 用户裁决前缀为 `@项目`（非早期预留的 `#项目`）。**推翻记录（2026-09-24）**：原条目为「`@项目` `#标签` 并补全」，随标签功能整体移除，`#标签` 部分同步删除，见下方标签推翻说明 |
| R-1.7 | 小窗列表初版为**单项目** | 记忆上次在小窗选择的项目 |
| R-1.8 | 未知 `@` **保存时创建** | 小窗输入中未匹配的 `@项目` 在保存时自动创建实体并绑定；已存在的走补全。用户裁决（2026-09-18）推翻「仅设置里创建」。**推翻记录（2026-09-24）**：原条目亦含 `#标签`，随标签功能移除同步删除 |
| R-2.6 | 以 **Default 项目** 取代「全部 / 未归属」切片 | 任务必须归属项目；不想填时落入 Default，保持 base-on-project 且零摩擦 |

**已裁决**：未知 token → 保存时创建（R-1.8，2026-09-18 修订）；归档见 R-4；Default 项目见 R-2.6。

**推翻记录（2026-09-24）——标签功能整体移除**：用户本轮原话「标签实际体验下来功能很累赘，可以考虑清理这个功能」，
推翻了 §4.2（下方）中「支持 todolist 添加更多标签」的原始需求，以及本节 R-1.6/R-1.8 中 `#标签` 相关表述。
标签不再是本项目的分类维度；「项目」维度不受影响，继续作为分类的唯一非优先级维度。
详见 [spec-remove-tag-feature](../specs/task-domain/spec-remove-tag-feature[IN-PROGRESS].md)。

**待设计决策**（不在本文回答）：列表可见行数上限、项目切换控件形态、
Windows 热键与系统冲突时的组合、Default 项目是否可删/可重命名。

### 4.1.1 完成与归档分离（容错）

**用户原话**：「勾选后不应该那么快的消失，应该先显示已完成（目前归档里面的实现）的划线低饱和状态……目前的方式没有容错，比如误触就必须进入归档才能回退，这明显不合理。」

**用户裁决（触发方式）**：「倾向用户手动触发，比如完整归档项目之类的操作才放入归档」（**不是**到时自动归档）。

| ID | 需求 | 说明 |
| :--- | :--- | :--- |
| R-4.1 | **完成 ≠ 归档** | 勾选完成只切换完成态（划线低饱和），任务仍留在活动列表 |
| R-4.2 | 完成态可**就地取消勾选**回退 | 无需进入归档视图 |
| R-4.3 | **显式归档动作**才进入「已完成归档」 | 将某项目下**已完成**任务列入归档，**保留项目来源**（不是「把项目整棵归档掉就消失」）；入口形态由 SPEC 裁决 |

> 这与 §6「撤销/重做」非目标**不冲突**：§6 排除的是命令栈式 Undo/Redo；
> 本条是完成态与归档态两个领域状态的分离。

### 4.2 主窗口：承载更丰富的分类能力

**用户原话（历史记录）**：「主页面里可以存在更加丰富的功能，支持 todolist 添加更多标签，比如项目、deadline 等做分类，单单目前看起来是优先级的 p1p2p3 不足以支撑。」

> **需求变更提示**：这**推翻了** design-domain-contract §3.4。
> 该处以「体量足以独立成篇」「筛选价值低于复杂度成本」为由
> 排除了标签与项目分组。现明确要求支持，且指出仅有 P1/P2/P3 三档优先级
> **不足以支撑**分类需求。
>
> **二次推翻记录（2026-09-24）**：上述原话中的「标签」分类维度已被用户本轮原话
> 「标签实际体验下来功能很累赘，可以考虑清理这个功能」推翻。标签相关的
> `Tag`/`TaskTag` 实体、设置页管理、任务侧多选已全部移除。「项目」「deadline」
> 两个维度不受影响，继续有效。

| ID | 需求 | 说明 |
| :--- | :--- | :--- |
| R-2.1 | 任务可归属**项目**进行分类 | 「项目」为用户明确点名的维度 |
| R-2.2 | 任务可设置 **deadline** | 用户明确点名。`DueDate` 字段已存在但无写入路径 |
| R-2.3 | 支持按**项目**维度**筛选/分组查看** | 分类的价值在于能据此筛选，否则只是装饰。**推翻记录（2026-09-24）**：原表述含「上述维度」（含标签），标签维度已移除 |
| R-2.4 | 任务创建后可**编辑** | 当前创建后除勾选与删除外无法修改任何内容，属基础空洞 |
| R-2.5 | 优先级保留，但不再是唯一分类维度 | 现有 P1/P2/P3 继续可用 |

**待设计决策**：项目是扁平列表还是支持层级、任务能否同时属于多个项目
（项目 vs 标签的语义区别）、deadline 是否需要时刻精度、
逾期任务如何呈现、分类的存储模型。

### 4.3 交付形态：可分发的 Windows exe

**用户原话**：「能构建 exe 作为第一目标。」

| ID | 需求 | 说明 |
| :--- | :--- | :--- |
| R-3.1 | 产出 Windows 可执行文件 | **第一优先级交付目标** |
| R-3.2 | 目标机器**无需预装 .NET 运行时** | 见下方现状核实 |
| R-3.3 | macOS 保持可开发可调试 | 开发环境为 macOS，不可退化 |

> **现状核实（重要）**：`publish/win-x64/FlowTask.Desktop.exe` 已存在，
> 但**不满足 R-3.2**。其 `runtimeconfig.json` 中
> `framework.name` 为 `Microsoft.NETCore.App`，属 **framework-dependent** 构建，
> 目标机器未安装 .NET 8 运行时将无法启动。
> 且产物为 43 个散落文件，并非
> [adr-technology-stack](../adr/adr-technology-stack.md) §2 承诺的「自包含单文件免安装包」。
>
> 换言之：**「能构建 exe」这一目标目前仅表面达成，实际未达标。**

**待设计决策**：self-contained 单文件 vs 目录分发、是否启用 trimming
（Avalonia + 反射的兼容性风险）、体积与启动速度取舍、是否配置应用图标
（当前 csproj 未配置 `ApplicationIcon`）。

### 4.4 参照标准

**用户原话**：「需要参考的是好的功能。」

即：不绑定特定竞品，以功能本身是否好用为准。

> **方法论约束**：此前 design-domain-contract 擅自引入 Things 3 与 Raycast 作为裁决标准，
> 而用户从未提及这两个产品。今后引用任何外部产品的做法时，
> 必须说明「这个做法为什么好」，而非以产品知名度充当论据。

## 5. 验收标准

本项目达成以下全部条件即视为核心目标完成：

1. **R-3**：能产出在纯净 Windows（无 .NET 运行时）上双击即运行的 exe；
2. **R-1**：小窗可在不碰鼠标、不打开主窗口的前提下完成「查看 → 勾选 → 添加 → 关闭」全流程；
3. **R-2**：任务可按项目与 deadline 分类并筛选，且创建后可编辑；
4. 全部机器门禁通过（`dotnet build` 零警告 + `dotnet test` 全绿）；
5. 文档与代码无漂移（Article 1）。

## 6. 非目标（明确不做）

| 不做 | 理由 |
| :--- | :--- |
| 多设备同步 / 云端 / 账号体系 | 本地优先是既定架构（adr-technology-stack），且与学习目标无关 |
| 团队协作 / 共享 / 指派 | 目标用户为单人（§2） |
| 移动端 | Avalonia 移动端是另一套平台适配课题，超出范围 |
| 富文本 / 附件 / 图片 | 渲染与存储成本高，学习价值低 |
| 遥测 / 崩溃上报 / 自动更新 | 学习项目不承担运营（§1） |
| 提醒通知 | 需后台调度器与平台通知权限，属独立能力，视精力再议 |
| 重复任务 / 循环规则 | RRULE 是独立复杂子领域，须先有稳定的单次任务模型 |
| 撤销 / 重做（命令栈） | 需引入命令栈，成本高于收益。**不包括** R-4 的「完成≠归档 / 取消勾选」 |
| 多语言本地化 | 当前全部文案硬编码于 axaml、无 `.resx`。目标用户为中文母语者，暂不投入 |

> 以上均为**有理由的显式排除**，非遗忘的待办（Article 4）。
> 「提醒通知」与「重复任务」标注为「视精力再议」，
> 若后续启用必须回到本文增补需求。

## 7. 需求与现状的差距总览

经代码核实的缺口，按需求归属：

| 需求 | 当前状态 | 差距性质 |
| :--- | :--- | :--- |
| R-1.1 小窗查看列表 | 小窗为 620×150 纯输入胶囊，无列表 | 需结构性改造 |
| R-1.2 小窗勾选完成 | 不存在 | 全新能力 |
| R-1.3 小窗快捷添加 | 已具备（`Enter` 保存） | 基本满足；缺 `@`/`#` |
| R-1.4 全程无鼠标 | 小窗呼出依赖主窗口前台 KeyDown / 按钮 | 部分缺失 |
| R-1.5 近似全局热键 | 仅主窗前台 Alt/Meta+Space | Windows 须抬到进程级 |
| R-1.6 `@`/`#` 捕捉 | 未解析 | 全新能力 |
| R-1.7 单项目列表 | 不存在 | 全新能力 |
| R-4.1～R-4.3 完成≠归档 | `IsCompleted` 即离开活动列表 | 契约级整改 |
| R-2.1 项目分类 | 数据模型无此概念 | 需扩展数据契约 |
| R-2.2 deadline | `DueDate` 字段存在但无 UI 写入路径 | 死字段，需接线 |
| R-2.3 按维度筛选 | 仅有 全部/今日/已完成 三视图，且「今日」恒为空 | 需重构筛选层 |
| R-2.4 任务可编辑 | 创建后无任何修改路径 | 功能空洞 |
| R-3.1 构建 exe | 已能构建 | 满足 |
| R-3.2 免运行时依赖 | framework-dependent，43 散落文件 | **未达标** |
| R-3.3 macOS 可调试 | `run.sh` 可用 | 满足 |

**额外的技术缺陷**（与需求无关，独立整改）：
`GetTodayTasksAsync` 时区区间错位、业务逻辑直接依赖系统时钟（违反 Article 9）、
`Description` 死字段、`PermanentDeleteAsync` 无调用方致软删除数据永久孤立。
详见 [design-domain-contract（技术缺陷已并入）](../archived/design-task-domain-superseded.md)。
