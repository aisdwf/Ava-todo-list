## 1. Why（付出的真实代价）

### 1.1 同一错误的两次变体

**第一次 —— design-domain-contract**：在项目无需求文档的情况下撰写设计，
以根目录 `README.md` 的产品宣传语（「捕捉灵感零负担」「高效思考者」）
作为裁决设计取舍的依据。

而 `README.md` 是与代码一同产出的自述文件，不是用户给出的需求。
即：**读取项目自己的宣传语当需求，再用它论证设计决策** —— 循环论证。
用户指出「没有需求如何开始 design？」，该文档被整体阻塞。

**第二次 —— design-domain-contract**：建立 REQUIREMENTS 后重写设计，
表面上修正了问题（每条决策标注了用户原话来源），
但**交互层的决策仍全部由撰写者自行推理**。典型如 §3.2：

> 分类不在创建时录入，而在创建后按需补充 ——
> 「这符合真实使用节奏 —— 灵感来时先记下，整理时再归类」

这句「符合真实使用节奏」是**未经证实的用户行为假设**，
且忽略了「用户已经在某个项目视图中」这一最强的意图信号。

依此实现后，用户实测评价：
「在某个创建的项目下新增一个内容，但是内容最后出现在全部任务，
还需要手动配置到项目才能纳入，这明显不符合直觉」。

同批被证伪的还有：手输标签（「对于后续的维护是灾难级的」）、
手输 `yyyy-MM-dd`（「谁会没事干完整的看一遍年月日」）、
点击展开编辑（「我根本没有发现这个 list 是可以点开配置的」）。

### 1.2 为什么第一次修正没有防住第二次

因为修正只针对了**论据的形式**（不再引用项目自述文件），
未针对**论据的性质**（主观判断冒充事实依据）。

「我读了 README 所以我知道用户要什么」和
「我推理出用户会先记后归类」——
论据来源不同，但**同属把撰写者的主观判断当作事实**。

### 1.3 为什么测试拦不住

design-domain-contract 落地为 spec-task-contract-and-clock / spec-classification-ui，共 163 个单元测试全部通过。
**测试断言的是「代码是否符合设计」，而错的是设计本身。**
自动化验证对这类缺陷完全无效。

## 2. Mandates（祈使式规则）

### 2.1 论据必须可追溯

1. 设计文档中每一条**交互决策**（用户如何操作、何时操作、操作后看到什么）
   **必须**可追溯至以下之一：
   - 用户的明确表述（**必须**引用原话）；
   - 对用户实际操作的观察记录；
   - 用户认可的参照产品的具体做法（**必须**说明"这个做法为什么好"，
     严禁以产品知名度充当论据）。

2. 凡不满足上述来源的判断，**必须**显式标注 `[推断]`
   并写明推断依据，供评审优先审查。

3. **严禁**使用以下句式为设计决策背书：
   - 「这符合真实使用节奏」
   - 「用户通常会……」
   - 「这更自然 / 更直觉」
   - 「一般来说……」

   除非紧随其后给出上述三类来源之一。

### 2.2 禁止自我循环

4. **严禁**引用项目自身产出的文档（README、产品介绍、既有设计文档中的
   未经证实判断）作为需求依据。
5. 需求层文档（`docs/requirements/`）是唯一的产品前提真源。
   设计文档若需新的产品前提，**必须**先回到需求层增补，
   而非在设计中自行设定。

### 2.3 交互方式不是实现细节

6. **严禁**把「字段如何录入」判定为实现细节而推迟决策。

   design-domain-contract §7.2 曾将到期日的输入方式列为
   「实现细节，不影响契约与结构，可在实施阶段确定」，
   实施时便退化为最省事的纯文本框，要求用户手输 `yyyy-MM-dd`。

   **录入方式直接决定可用性，属设计决策。**

### 2.4 存疑时提问而非推断

7. 当某个交互点缺少用户明示且无法从既有依据推出时，
   **必须**列为待裁决问题向用户提问，**严禁**填入自己的倾向后继续。
8. 提供选项时**必须**给出各方案的真实权衡，
   **严禁**只呈现自己偏好的方案或用引导性描述影响选择。

## 3. 正反示例

### ❌ 违规（design-domain-contract §5 原文）

> **代价**：明确知道归属的任务无法一步创建到位（先建后归类，两步）。
> **接受理由**：原则 1 优先级最高。为少数「创建时已知归属」的场景
> 在主路径上添加控件，会损害全部创建操作的速度。

问题：「少数场景」是凭空断言的频率判断；
「损害速度」未经任何测量；结论与用户的实际直觉相反。

### ✅ 合规

> **[推断]** 单任务标签数上限 5 个，任务行显示前 2 个，其余折叠为 `+N`。
> **推断依据**：任务行需为标题保留主要横向空间（Editorial 排版基调），
> 实测 1180px 窗宽下超过 2 个标签会明显压缩标题区。
> 具体数值需在实施时依实际渲染效果微调，此处为待确认的初值。

区别：明确标注为推断、给出可检验的依据（窗宽与渲染效果）、
声明需要确认而非当作已定结论。

## 4. 机器检查

本规则难以完全自动化，但可做**关键词软扫描**：

```bash
# 扫描设计文档中的无据断言句式
grep -rnE '符合(真实)?(使用)?(习惯|节奏)|用户(通常|一般|往往)|更(自然|直觉)' \
  docs/design/*.md | grep -v '\[推断\]'
```

命中不代表违规（可能紧随其后给出了合规来源），
但**必须**人工复核该处是否满足 §2.1。

> **诚实声明**：本规则的核心要求（论据性质是否为主观判断）
> 无法由机器判定，最终依赖评审。
> 因此**用户审核是本规则唯一可靠的执行手段** ——
> 这与 [rule-spec-review-gate](./rule-spec-review-gate.md) 互为支撑：
> 跳过审核则本规则必然失效。

---

## 5. 例外

无例外。若确实无法取得用户明示且必须推进，
正确做法是标注 `[推断]` 并列入待裁决问题，而非省略标注。
